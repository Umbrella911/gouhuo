  def         带 * 的是 Windows 当前的默认端点
  bus         总线枚举器。HDAUDIO/USB/PCI/BTH* 是真硬件，其余是软件设备（虚拟声卡）
  mix-format  共享模式引擎的格式。不是 48 kHz 的话我们每一帧都要过重采样
  cur-ms      当前生效的共享模式引擎周期 —— 这是共享模式延迟的主项
  engmin-ms   IAudioClient3 允许申请到的最小引擎周期（Win10+ 的低延迟共享模式）
  devdef/min  GetDevicePeriod 的 default 和 minimum，后者是独占模式的周期下限
  excl-48k    独占模式接不接受 48 kHz 16 位

==== 这台机器的可用余地 ====
  渲染：真硬件 5 个｜当前周期 10.00 ms｜低延迟共享最小 10.00 ms｜独占最小 3.00 ms
  采集：真硬件 3 个｜当前周期 10.00 ms｜低延迟共享最小 10.00 ms｜独占最小 3.00 ms

  注意：默认渲染端点「SteelSeries Sonar - Gaming (SteelSeries Sonar Virtual Audio Device)」是软件设备（bus=ROOT）。
        它在真硬件之上又叠了一层用户态路由，延迟会比硬件本身高。
        定红线要用真硬件端点的数字，但用户实际经历的是这个。

  mode@queue   渲染的 @N 是**实际维持的队列深度**，也就是渲染吃掉的延迟
  p50/p95/max  采集：设备记录到我们拿到手的实测延迟
               渲染：欠载余量（补数据前队列还剩多少）。**不是延迟**，
               离咔哒声还有多远。余量 = 队列深度 - 一个周期
  buf-ms       Initialize 实际给到的缓冲时长
  rep-ms       驱动自报的 GetStreamLatency。0 说明驱动压根没填，别当回事
  wake95       事件唤醒间隔的 p95。跟周期差太多说明线程醒不准，低延迟是假的
  glitch       采集的数据不连续 / 渲染的欠载。不是 0 说明这个配置扛不住

====================================================================================
M2 结论：设备到底吃掉多少
====================================================================================

  shared 模式（只算真硬件端点）
    采集实测 p95        10.27 ms
    渲染理论下限        10.02 ms（shared@10.0）
                        零欠载，但余量可能只有一帧 —— 漏醒一次就咔哒
    渲染可用工作点      20.00 ms（shared@20.0，余量 >= 一个周期）
    合计（按可用工作点）30.27 ms

  对账 M1 的假设：
    协议 46.5（M1 实测）+ 设备 30.3（本次实测）= 端到端 76.8 ms，红线 120
    >>> 进线，余量 43.2 ms
    redline::DEVICE_BUDGET_MS = 30.4 ms，本次实测 30.3 ms，差 -0.1 ms

  这个数字**不**代表所有用户：
    - 虚拟声卡（SteelSeries Sonar / 雷蛇 / Voicemeeter / 直播虚拟线）没算进来。
      它们在真硬件之上再叠一层，用户实际延迟只会更高，不会更低。
      上面表里虚拟设备测出来比硬件还低，那不是更快，是这种量法测不到它的上游。
    - 蓝牙耳机没算进来，那是另一个量级（编解码器本身就几十毫秒）。

  还没测的：
    - 声学往返（音箱 → 空气 → 麦克风）。要出声，得单独做
    - APM（AEC3/降噪/AGC）的延迟与 CPU
    - 采集和渲染两个时钟不同步时的重采样代价

==== APM（AEC3 / 降噪 / AGC2 / 高通）====
不碰设备、不出声。每块单独计价，最后是实际要发布的全开配置。

全开（实际配置）                     64.9       92.3     0.65%      15.00     1.00     0.948
------------------------------------------------------------------------------------
  p50/p95-us  每 10 ms 帧的处理耗时（近端 + 远端两次调用）
  cpu%        折算成单核占比。产品线 6%，但那是**整个通话**的预算，
              APM 要跟 Opus 编解码共享（M1 实测编解码 2.18%）
  delay-ms    互相关量到的波形延迟。APM 不会自报这个数，只能测
  peak        相关峰。低于 0.5 就判定认不出来了，宁可不报数
  level       输出/输入幅度比。AGC 会明显改它，接近 0 说明信号被吃掉了

====================================================================================
M2 完整结论：协议 + 设备 + APM
====================================================================================
  延迟：协议 46.5（M1）+ 设备 30.4（M2）+ APM 15.00 = 91.9 ms，产品线 120
    >>> 进线，余量 28.1 ms
    防回归闸 100 ms：在闸内
  CPU：APM 0.65% + 编解码 2.18%（M1）= 2.83%，产品线 6%
    >>> 进线，余量 3.17 个百分点
    防回归闸 4%：在闸内
    注意这是单路。频道里 K 个人同时说话，解码要乘 K，APM 不用。

  仍然没测的：
    - 真回声下 AEC3 的效果（这里远端喂的是静音，没有回声可消）
    - 声学往返（音箱 → 空气 → 麦克风）
    - 虚拟声卡那一层、蓝牙耳机
    - 内存和安装包红线（要等 voice-core 独立进程和 Tauri 打包）
