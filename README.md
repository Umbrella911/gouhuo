# 开麦 / kaimai

> Mumble 的现代化重写，为中国玩家做。开源、可自部署、只做 Windows 原生客户端。

场景是 3–20 人的朋友或公会，常驻一个频道，边打游戏边说话，一挂几小时。
所有设计以「常驻几小时不打扰人」为准绳，不是以「功能齐全」为准绳。

名字就是这软件干的事，不用解释。**刻意避开「开黑」**：KOOK 的前身就叫开黑啦，
那块心智已经被占死了，蹭不到，只会被比下去。

**当前进度：M1、M2 完成。端到端实测 91.9 ms，破 80 ms 红线 11.9 ms ——
详见下面的 M2 结论。还没有 UI，只有两个探针。**

## 红线

破线算 bug，不算优化项。这几条是这个项目唯一真正的差异化，松一次就回不去了。

| 指标 | 红线 | 实测 |
|---|---|---|
| voice-core 常驻内存 | < 60 MB | 未测（要等 voice-core 拆成独立进程） |
| 通话中 CPU（单核占比） | < 3% | **2.84%** = 编解码 2.18% + APM 0.66%。只剩 0.16 个百分点 |

## M1 结论

**GO —— 但帧长这个旋钮上出现了一个必须解决的冲突：延迟要 10 ms 帧，带宽要 20 ms 帧。**

完整报告存档在 [`docs/m1-baseline.txt`](docs/m1-baseline.txt)，下面的数字都出自那一份。

测法：不接音频设备，喂合成信号打时间戳，走完整的
「Opus 编码 → 加密 → UDP → 服务端转发 → 抖动缓冲 → 解码 → 播放」链路。
拿到的是不掺设备延迟的干净数字，也就是这套架构的物理下限。

延迟同时用两套**互相独立**的方法量，对得上才算数：

1. 墙钟：播放时刻 − 采集时刻，加一帧（渲染侧摊开）加 Opus 前瞻
2. 信号域：拿播出的 PCM 跟参考信号做归一化互相关，直接量波形延迟

两者在所有配置下都对到 0.1 ms 以内。任何一次测量对不上账，报告里会直接标
「别信这一行」。

### 主要数字

测试机：AMD Ryzen 7 5700X3D（8C16T）/ Windows 11 Pro / rustc 1.96 MSVC / release 构建。
网络档 `city` = 单程 12 ms、抖动 σ=4 ms、丢包 0.5%（客户端→服务端→客户端两跳合计）。

| 帧长 | 缓冲深度 | 协议嘴到耳 p95 | 欠载 | 判定 |
|---|---|---|---|---|
| 10 ms | 1 帧 | 46.6 ms | 1 | 延迟够但音质不行 |
| **10 ms** | **2 帧** | **46.5 ms** | **0** | **可用** |
| 10 ms | 3 帧 | 56.6 ms | 0 | 音质够但超预算 |
| 20 ms | 2 帧 | 66.5 ms | 0 | 音质够但超预算 |
| 20 ms | 3 帧 | 86.6 ms | 0 | 音质够但超预算 |

80 ms 的预算里，协议部分占 46.5 ms，**还剩 33.5 ms 给 WASAPI 采集 + 渲染**。

延迟各项的量级（10 ms 帧 / 缓冲 2 帧 / city）：

```
打包（一帧攒满才能编）        10.00 ms
Opus 编码器前瞻               6.50 ms   <- 编码器自报，互相关能对上
编码 p95                      0.26 ms
网络（两跳合计）             12.00 ms
服务端转发 p95                0.05 ms   <- 转发器就是个 UDP 中继，几乎不要钱
抖动缓冲（2 帧）             20.00 ms
解码 p95                      0.06 ms
渲染侧摊开一帧               10.00 ms
```

**这几项不是加法。** 包在网上飞的时候缓冲也在填，两段是重叠的。真正成立的是：

```
墙钟   ≈ 网络单程 + (缓冲深度 − 1) × 帧长 + 采集/播放两个时钟的相位差(0 ~ 一帧)
嘴到耳 = 墙钟 + 一帧（渲染侧摊开）+ Opus 前瞻
```

代进去：`12 + 10 + ~8 = 30.0` 墙钟，`30.0 + 10 + 6.5 = 46.5` 嘴到耳。实测 46.5。

**编解码加起来 0.32 ms，服务端转发 0.05 ms。** 自研传输这个决定在延迟上完全成立 ——
协议栈本身根本不是瓶颈，抖动缓冲和帧长才是。

### 三个必须记住的发现

**1. 帧长的取舍是「延迟 + CPU」对「带宽」，不是三者对一者。**

| 帧长 | 每包固定开销 | 固定开销折算 | Opus 16k 时说话带宽 | 编解码 CPU |
|---|---|---|---|---|
| 10 ms | 57 B | 45.6 kbps | 61.3 kbps | 2.18% |
| 20 ms | 57 B | 22.8 kbps | 39.0 kbps | 2.75% |

固定开销 57 字节 = IP/UDP 头 28 + 我们的包头 13 + AEAD tag 16。
**10 ms 帧下，还没编码一个比特，固定开销就已经 45.6 kbps，40 kbps 的红线当场破。**

反直觉的是 CPU：10 ms 帧**更省**。Opus 单帧编码成本随帧长超线性增长
（20 ms 一帧 481 µs vs 10 ms 一帧 190 µs，2.5 倍不是 2 倍），按秒摊反而短帧便宜。

这个冲突必须在 M3 解决，可动的地方（都还没做）：

- 包头 13 → 7 字节：`timestamp` 在定长帧下可由 `seq` 推出，`session` 用 u16
- AEAD tag 截短到 8 字节（SRTP 的常规做法）
- Opus 码率降到 16 kbps

三条加起来在 10 ms 帧下能省约 21 kbps，刚好把 61.3 压到红线内。
在做完这个之前，10 ms 帧只是「延迟上可行」，不是「可以发布」。

**2. 固定抖动缓冲每欠载一次，延迟就阶梯式上涨，而且再也不下来。**

表里 `10 ms / 缓冲 1 帧` 的延迟跟 `缓冲 2 帧` 一模一样（46.6 vs 46.5），就是这个原因：
它欠载了一次，重新预缓冲，攒到的深度就回不去了。所以「把缓冲调浅」在固定缓冲上
根本换不到低延迟，只换到一次听得见的卡顿。

这正是[自适应抖动缓冲（M4）](#路线图)要解决的问题，也是「没法一边把低延迟当卖点，
一边用别人给通用场景调的缓冲策略」这句话的实证。

`bad` 档（抖动 σ=15 ms）下，缓冲 1 帧欠载 4 次、听感丢帧 7.8%；
要压到 0 次欠载得把缓冲加到 2 帧，代价是延迟涨到 76.5 ms。

**3. Windows 上有两个会默默吃掉语音包的坑，都已经修在 `voice-core::net` 里。**

- **不要用 `SO_RCVTIMEO` 轮询退出标志。** Winsock 的读超时跟正在到达的数据报
  撞车时会把整个数据报丢掉。读超时周期一旦接近帧间隔就会周期性撞上：
  20 ms 超时 + 20 ms 帧在**纯回环、零网络损伤**的链路上稳定丢约 0.5%，
  同一份代码换成 10 ms 帧一个不丢。抓包工具里看不见，只表现为「偶尔咔哒一下」。
  正确做法是一直阻塞在 `recv_from` 上，用哨兵包唤醒。
- **UDP 默认接收缓冲只有 8 KB。** 收包线程被调度器晾一下，或者七八个人同时说话，
  缓冲就满了，内核默默丢包不报错。

还有一个不是 bug 但同样致命的：Windows 默认定时器粒度 15.6 ms，
`sleep(20ms)` 实际可能睡 31 ms。必须 `timeBeginPeriod(1)` 加自旋收尾，
见 `voice-core::clock`。

### 这些数字**不**包括什么

不写清楚就是自欺欺人：

- WASAPI 采集 + 渲染延迟（M2，这是 80 ms 里最后一块拼图）
- APM（AEC3 / 降噪 / AGC）的延迟与 CPU。AEC3 是这条链路上最贵的一块
- 真实公网的抖动分布 —— 这里用的是高斯，真网络是重尾的
- 多人同时说话时服务端转发的扇出开销
- 下行带宽：K 个人同时说话就是 K 倍，红线只管住了单条上行
- 内存和安装包红线

另外，延迟矩阵里采集和播放两个时钟的相位差被刻意钉在了最坏的一端
（为了让互相关的滞后一定为正），所以表里的数字比真机平均值**偏高约半帧**。

预算里那 30 ms 的设备额度是**假设不是实测**，依据是共享模式下采集和渲染各约一个
10 ms 引擎周期加混音器一跳。M2 的第一件事就是把它换成实测值。

## M2 结论（设备部分）

**设备吃掉 30.4 ms。端到端 76.9 ms，进线 —— 但余量只剩 3.1 ms，而 APM 还没接。**

完整报告存档在 [`docs/m2-baseline.txt`](docs/m2-baseline.txt)。

测法：真开 WASAPI 流，但**不出声**。渲染全程灌静音；采集不需要麦克风前面有声音 ——
`IAudioCaptureClient::GetBuffer` 的 `pu64QPCPosition` 就是「这一包第一个采样点被设备
记录下来的那一刻」，跟我们拿到手的时刻一减就是采集延迟。

| 路径 | 实测 | 是什么 |
|---|---|---|
| 采集 | 10.37 ms | 一个引擎周期。WASAPI 时间戳直接量到的，没得选 |
| 渲染 | 20.00 ms | 我们维持的队列深度。**这是设计选择，不是物理限制** |

### 渲染那 20 ms 是一个可以翻案的决定

渲染的物理下限是 **10.02 ms**（一个周期多一帧），实测五秒零欠载。
但那个工作点的余量只有**一帧** —— 线程漏醒一次就是一声咔哒，而这软件是要跟游戏
抢 CPU 的。取 20 ms 是为了留住整整一个周期的余量，扛得住漏醒一次。

想换回 10 ms 也行：那是拿「偶尔咔哒」换 10 ms 延迟，端到端会从 76.9 掉到 66.9。
这是产品决定不是技术决定，所以摆在这儿，不藏在代码里。

### 三个发现

**1. `IAudioClient3` 的低延迟共享模式在这台机器上没有红利。**

Win10 之后共享模式也能把引擎周期压到驱动支持的最小值，不用走独占。但这台机器上
所有真硬件端点报的 `engmin` 都等于 `engdefault`（10 ms）—— 驱动不配合，这条路是空的。
讽刺的是虚拟声卡反而报 2 ms，因为它不是真硬件，可以随便报。

**2. 独占模式不能用，而且这台机器上根本没测起来。**

独占能把周期压到 3 ms，但独占期间**游戏本身发不出声** —— 开黑软件不可能用它。
本来只想拿它标定上限，结果渲染路径报
`AUDCLNT_E_BUFFER_SIZE_ERROR`，采集路径的时间戳又恒等于 0。所以这条只留了个能跑的
代码路径，没有可信数字。

**3. 默认端点是虚拟声卡，而虚拟声卡的延迟测不准。**

这台机器的默认收发端点都是 SteelSeries Sonar —— 这在中国玩家里极其常见
（Sonar、雷蛇 Synapse、Voicemeeter、直播软件的虚拟线）。它们是用户态音频路由，
在真硬件之上再叠一层。

麻烦的是它们测出来**比真硬件还低**（采集 0.42 ms vs 硬件 10.37 ms）。那不是更快，
是这种量法测不到它的上游：虚拟设备自己造 QPC 时间戳，只覆盖「路由把数据递给我们」
那一段。所以探针里加了一条判据：**采集延迟小于四分之一个周期就判定时间戳不可信**
（音频物理上至少要攒够一个周期才可能交付），不可信的一律不进预算。

真实用户的延迟 = 硬件那一层 + 虚拟声卡那一层，只会比 30.4 ms 更高。这一层目前测不到。

### APM：AEC3 吃掉 15 ms，这是压垮红线的那一根

`webrtc-audio-processing` 开箱在 Windows/MSVC 上编不过。`third_party/` 下是打过
补丁的副本，六处补丁全部用 `kaimai patch:` 标出来了，诊断和复现配方见
[`docs/m2-apm-windows.md`](docs/m2-apm-windows.md)。补丁应该提给上游，合并之后
删掉整个 `third_party/` 即可。

逐块计价（10 ms 帧，近端 + 远端两次调用）：

| 配置 | CPU | 延迟 |
|---|---|---|
| 全关（基线） | 0.04% | 0.00 ms |
| 只开 AGC2 | 0.04% | 0.00 ms |
| 只开 高通 | 0.14% | 1.00 ms |
| 只开 降噪 | 0.21% | 7.00 ms |
| 只开 AEC3 | 0.58% | 9.00 ms |
| **全开（实际配置）** | **0.66%** | **15.00 ms** |

延迟是互相关量出来的（APM 不自报这个数），并且用**冲激法独立验过一遍** ——
整条红线过不过压在这个数上，一种量法不够。

**AEC3 和降噪占了 APM 全部 15 ms 里的绝大部分**，而这两块都不是可选的：
没有 AEC3 外放开黑就啸叫，没有降噪机械键盘声直接糊到队友耳朵里。

顺手量到两件事：

- APM 强制 **10 ms** 处理帧（`audio_processing.h:83`）。打包粒度不受影响，
  20 ms 一个包跑两次 APM 即可 —— 不改变 M1 的帧长结论
- 静态库 strip 之后 **38 MB**。这不等于安装包大 38 MB（链接器会丢死代码），
  但 30 MB 红线摆着，M5 打包时必须实测

### 红线破了：91.9 ms

```
协议链路   46.5 ms   （M1：10 ms 帧 + 缓冲 2 帧 + 同城两跳）
设备       30.4 ms   （M2：采集 10.4 + 渲染队列 20.0）
APM        15.0 ms   （M2：AEC3 + 降噪 + AGC2 + 高通）
--------------------
合计       91.9 ms   红线 80 ms，破 11.9 ms
```

要找回这 11.9 ms，能动的只有这几个旋钮，**每一个都有真实代价**：

| 旋钮 | 省 | 代价 |
|---|---|---|
| 渲染队列 20 → 10 ms | 10.0 ms | 余量只剩一帧，线程漏醒一次就是一声咔哒 |
| 关掉降噪 | ~6 ms | 机械键盘、风扇、空调声直接传出去 |
| 抖动缓冲 2 帧 → 1 帧 | 10.0 ms | M1 实测会欠载，延迟还会阶梯式涨回去 |
| 关掉 AEC3 | ~9 ms | 外放直接啸叫，等于这个场景不能用 |

单拉一个都不够（最多省 10 ms），要进线至少得动两个。

**也可能是 80 ms 这条线本身定得过紧。** M2 的价值就在这儿：在
「AEC3 + 共享模式 WASAPI + 留得住余量的渲染队列」这个组合下，80 ms 物理上做不到。
要么放弃其中一项，要么把线放到 ~92 ms。这是产品决定不是技术决定，
所以摆在这儿，没有偷偷调红线。

### 这些数字**不**包括什么

- **真回声下 AEC3 消得干不干净。** 测延迟和 CPU 时远端喂的是静音，没有回声可消。
  效果好不好要真声学环境才测得了
- 声学往返（音箱 → 空气 → 麦克风）。要出声，得单独做
- 虚拟声卡那一层、蓝牙耳机（那是另一个量级，编解码器本身就几十毫秒）
- 采集和渲染两个时钟不同步时的重采样代价

数字来自一台机器：Ryzen 7 5700X3D + Arctis Nova Pro Wireless（USB）+ Realtek，
共享模式引擎周期 10 ms。

## 怎么跑

需要 Rust（MSVC toolchain）和 CMake（`audiopus_sys` 要从源码编译 libopus）。
Visual Studio / BuildTools 自带的那份 cmake 就行，`scripts\m1.ps1` 会自己找。

```bash
cargo test --workspace
```

```bash
cargo run --release -p latency-probe
```

默认跑完整矩阵：四档网络 × 10/20 ms 帧 × 缓冲 1/2/3 帧，每个配置 6 秒，
外加带宽表和 CPU 成本表，最后给 GO/NO-GO 结论。约 3 分钟。

要门禁级的可信数字就把时间拉长（p99 需要样本），并且**跑的时候别动这台机器** ——
后台一个编译就能把 p99 毁掉：

```powershell
.\scripts\m1.ps1 -Seconds 30
```

只看一个配置的详细分解：

```bash
cargo run --release -p latency-probe -- --single --profile city --frame-ms 10 --target 2
```

其余参数见 `--help`。`--seed` 可以精确复现某一次的网络仿真，
排查「上次 p95 是 41 ms 这次是 58 ms」时用得上。

### M2：设备延迟 + APM

```bash
cargo run --release -p device-probe
```

**不会出声**，但会短暂点亮「麦克风正在使用」指示灯 —— 测采集必须打开采集流。
只看设备能力、不打开任何流加 `--list`；跳过 APM 那段加 `--no-apm`。

加 `--exclusive` 会顺带测独占模式，**那几秒里别的程序发不出声**。

**Windows 上首次构建要额外准备**（APM 要从源码编 libwebrtc）：

```bash
pip install meson ninja
rustup component add llvm-tools
```

还要从 MSVC 开发者环境里跑（meson 要在 PATH 上看得见 `cl.exe`），并把
`LIBCLANG_PATH` 指向一份 libclang（VS 自带的就行）。
细节和踩过的坑见 [`docs/m2-apm-windows.md`](docs/m2-apm-windows.md)。

## 结构

```
crates/
  protocol/        客户端与服务端共享的唯一一份协议定义：包格式、序列化、加密
  voice-core/      客户端语音内核。目前含抖动缓冲、实时时钟、socket 调优、
                   WASAPI 采集/渲染、度量、红线定义
  latency-probe/   M1：协议链路延迟
  device-probe/    M2：WASAPI 设备延迟 + APM
third_party/
  webrtc-audio-processing-sys/  打过 Windows 补丁的副本，补丁标了 `kaimai patch:`
docs/
  m1-baseline.txt     M1 的完整报告存档
  m2-baseline.txt     M2 的完整报告存档
  m2-apm-windows.md   APM 在 Windows 上编不过的诊断和补丁说明
```

README 里的每个数字都出自这两份存档。

`protocol` 两端都依赖，改一个字段两边同时编译报错 —— 这就是把它独立成 crate 的
全部理由。`voice-core` 完全独立于 UI，将来实测内存不达标时把它拆成独立进程加托盘
常驻是纯工程重构，不需要重写任何逻辑。

## CI

`cargo fmt --check`、`clippy -D warnings`、`cargo test` 是门禁。

**延迟数字在 GitHub 托管 runner 上只记录、不门禁。** 那是虚拟化的共享机器，
节拍器迟到是常态，测出来的 p95 反映的是 runner 的负载而不是我们的架构；
在那种数字上设门禁只会训练出「重跑一次就绿了」的习惯，比不测更糟。
真门禁跑在专用机器上，见 [`.github/workflows/redline.yml`](.github/workflows/redline.yml)。

## 路线图

- **M1** ✅ 协议链路延迟下限
- **M2** ✅ 设备 30.4 ms + APM 15.0 ms 都已实测。
  **结论是端到端 91.9 ms，破 80 ms 红线** —— 往下走之前需要一个产品决定：
  动哪个旋钮，还是放宽红线
- **M3** 控制面（TCP + TLS）、密钥协商（Noise / 从 TLS 派生）、服务端、
  **包头瘦身**（见上面第 1 条发现）、邀请链接
- **M4** 自适应抖动缓冲 + PLC。这是项目技术含量最高的地方，也是低延迟卖点的主战场
- **M5** Tauri UI、全局热键、TTS 播报、提示音

### 明确不做

视频、屏幕共享、动态/帖子/社区发现/好友系统、装扮和表情商店、富文本、
长期消息历史、直播。macOS/Linux 客户端、web 客户端、移动端。
